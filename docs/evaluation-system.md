# 评测体系说明

## 评测指标体系

### 1. 系统性能指标

| 指标 | 定义 | 计算方式 |
|------|------|---------|
| 完整响应时间 | 从用户输入到回答完成的总时长 | 单次对话端到端耗时 |
| Token消耗量 | 单次对话的输入+输出Token总数 | Dify API返回的usage |
| 对话完成率 | 成功执行并返回回答的比例 | 成功数 / 总数 |
| 错误率 | 执行失败的比例 | 失败数 / 总数 |

### 2. 工具调用指标

| 指标 | 定义 |
|------|------|
| MCP调用成功率 | 库存/物流MCP工具成功返回的比例 |
| 工具调用延迟 | MCP工具从调用到返回的耗时 |

### 3. RAG质量指标（RAGAS自动化）

仅对需要RAG的场景计算（产品咨询、店铺政策、促销活动、投诉、技术支持）。

| 指标 | 定义 | 说明 |
|------|------|------|
| Faithfulness（忠实度） | 回答是否基于检索到的上下文 | 0-1，越高越好，衡量幻觉率 |
| Answer Relevancy（回答相关性） | 回答与用户问题的相关程度 | 0-1，越高越好 |
| Context Recall（上下文召回率） | 检索到的上下文是否覆盖标准答案所需信息 | 0-1，越高越好 |

### 4. 回答内容指标

| 指标 | 定义 | 计算方式 |
|------|------|---------|
| 回答完整率 | 用户所有子问题被回答的比例 | LLM自动评判：问题含N个子问题，回答覆盖M个，完整率=M/N |

### 测试集字段

```json
{
  "id": 1,
  "question": "静语降噪耳机Pro2续航多久",
  "expected_scene": "产品咨询",
  "type": "RAG",
  "sub_questions": ["续航时间"]
}
```

- `type`: "RAG" 表示需要计算RAGAS指标，"non-RAG" 表示不需要
- `sub_questions`: 用于回答完整率评估的子问题列表

### 边界case设计

- 多子问题："RTX5080多少钱，有货吗，什么时候发货"（3个子问题）
- 运单号查询："ZT444333222111发的什么快递"
- 语义不完整："我想咨询一下"
- 无关请求："帮我订个外卖"
- 乱码输入："asdfghjkl"
- 路由边界："质量问题退换货运费谁出"（政策vs投诉边界）

## 评测方法

### 每条3次取最优

由于LLM路由存在偶发不稳定性（同一问题多次调用可能路由到不同分支），每条测试用例跑3次，取评价最好的一次作为最终结果。

**选择优先级**：
1. 执行成功 > 执行失败
2. 路由正确 > 路由错误
3. Faithfulness高 > Faithfulness低
4. 回答完整率高 > 完整率低

### 评测流程

```
for each test_case (104条):
    for attempt in 1..3:
        1. 调用Dify API（streaming模式）
        2. 记录响应时间、Token消耗、是否成功
        3. 解析回答内容，判断实际路由
        4. 提取MCP调用记录（库存/物流）
        5. 对RAG场景调用RAGAS评估（Faithfulness/Answer Relevancy/Context Recall）
        6. 调用LLM评判回答完整率
    取3次中最优结果
```

### RAGAS评估实现

使用DeepSeek API作为评判模型，通过Prompt工程模拟RAGAS指标：

- **Faithfulness**: 让LLM判断回答中的每个陈述是否能从检索上下文中找到依据
- **Answer Relevancy**: 让LLM判断回答是否直接回应了用户问题
- **Context Recall**: 让LLM判断标准答案所需信息是否都出现在检索上下文中

### 回答完整率评估（LLM-as-Judge）

Prompt设计：
```
用户问题包含以下N个子问题：[子问题列表]
请判断回答覆盖了其中几个，返回格式：覆盖数M/总数N
```

评分规则：0, 1/2, 2/3, 3/3, 4/4 等均有可能。

## 迭代闭环

```
发现BadCase → 归因分析 → 调整提示词/分类器/知识库 → 重新评测 → 验证改进
```

### 已修复的关键问题

1. **物流数据读取为空**：MCP返回格式从JSON改为纯文本
2. **兜底分支失效（0%）**：修复兜底节点连接
3. **店铺政策vs投诉路由混乱**：明确分类器边界（"询问规则"归政策，"表达不满"归投诉）
4. **会员权益路由错误**：分类器加入会员/积分/优惠券关键词
5. **投诉Faithfulness仅0.35**：加强投诉回答提示词"仅根据知识库回答"约束
6. **618活动召回失败**：升级父子分段+切换嵌入模型
